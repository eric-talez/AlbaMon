# K-Work US 캘리포니아 무료 공개 출시 설계

작성일: 2026-09-09. 기준 커밋: c8de0c8. 상태: 실행 전 검토용 설계.

## 1. 이번 계획의 기준

사용자가 확정한 방향은 **캘리포니아 우선, 무료 공개 출시, 사용자 1명이 개발·PM·총괄을 맡고 Codex가 개발을 지원**하는 것이다. 가입을 초대로 제한하는 서비스로 출시하지 않는다. 출시 전 staging 검증과 소규모 리허설은 공개 출시를 준비하는 과정이다.

기존 PRODUCT_BRIEF와 2026-06-20 PDF의 LA/OC 한정·전국 확장·유료 부스트 로드맵보다 이번 결정이 우선한다. 기존 코드는 유지하고 출시를 막는 빈틈을 보완한다. 이번 산출물은 점검과 실행 계획이며 실제 코드 수정, 계정 생성, 유료 구매, 외부 발송, 배포는 수행하지 않았다.

### Global Constraints

- 첫 출시의 공개 공고는 캘리포니아 근무지(state = CA)만 허용한다.
- 구직자와 고용주 모두 무료로 이용하며 결제·부스트를 추가하지 않는다.
- 제품명은 K-Work US를 유지한다.
- 한국어 중심 UI와 주요 안내의 영어 병기를 유지한다.
- 커뮤니티 특화와 직무상 한국어 능력 요건을 지원하며 국적·민족에 따른 지원 제한을 만들지 않는다.
- Next.js App Router, TypeScript, Tailwind, Supabase Auth/Postgres/RLS를 유지한다.
- 사용자 데이터 접근은 검증된 세션과 DB 권한으로 제한하며 사용자 입력의 role을 신뢰하지 않는다.
- 운영 빌드와 운영 런타임에서 샘플 공고를 공개하지 않는다.
- 사용자 흐름에서 service-role 키를 사용하지 않는다. 알림 worker와 통제된 운영 작업에만 사용한다.
- 운영 DB에서 reset 또는 seed를 실행하지 않으며 기존 migration을 수정하지 않는다.
- 실제 공개 전 RLS 통합 테스트, 주요 브라우저 흐름, 정책 게시, 복구 리허설을 통과한다.
- 자동 결제, 전국 확장, AI 매칭, 이력서 파일 업로드, 실시간 채팅은 첫 출시 범위에서 제외한다.

## 2. 현재 위치와 선택한 접근

핵심 기능은 이미 있다. 새 프로젝트를 만들 단계가 아니라 **동작하는 채용 흐름을 운영 가능한 상태로 만드는 단계**다. 상세 근거와 검증 한계는 [저장소 점검](../audits/2026-09-09-repository-audit.md)에 있다.

| 접근 | 장점 | 비용/제약 | 판단 |
|---|---|---|---|
| 기존 Next.js + Supabase 보완, 사람의 공고 승인 유지 | 구현한 지원·메시지·관리자 기능 재사용, 운영 판단이 명확함 | 승인과 신고 처리는 대표의 시간이 필요함 | 추천 |
| 공개 공고와 외부 연락처만 남기는 게시판 | 구현·알림 부담 감소 | 개인정보 노출과 사기 대응이 어려워지고 기존 지원 관리의 가치가 사라짐 | 현재 저장소에는 이점이 작음 |
| 자동 승인·사업자 검증·매칭까지 확장 | 장기적으로 수작업 감소 가능 | 외부 서비스, 오탐 대응, 비용, 검증 범위 증가 | 실사용 데이터가 쌓인 뒤 재평가 |

## 3. 공개 범위와 제품 경험

### 구직자

로그인 없이 CA 공고를 검색한다. 도시, 업종, 고용 형태, 언어 요건, 급여 단위/하한, 최신순으로 찾고 상세에서 지원한다. 첫 로그인 후 표시 이름과 검증된 이메일을 확보한다. 지원은 현재의 1,000자 소개 방식으로 유지하고 이력서 파일은 받지 않는다.

지원 현황, 고용주 답변, 본인의 지원 철회를 제공한다. 고용주가 구직자의 의사 없이 withdrawn으로 바꿀 수 없다. 기존 구직자가 고용주로 승격되어도 이전 지원 기록과 본인이 참여한 대화는 보존한다. 새 구직 지원은 seeker 역할만 허용하는 현재 정책을 유지한다.

### 고용주

Google 로그인 → 고용주 권한 신청 → 대표 검토 → 회사 등록 → 공고 제출 → 승인 후 공개의 기존 흐름을 유지한다. 가입은 공개이며 **고용주 권한과 공고 공개는 각각 심사**한다.

공고를 편집하면 pending으로 돌아가 재심사한다. 모집 마감은 즉시 가능하다. 마감/중지된 공고에 신규 지원은 불가능하지만 기존 지원·대화는 보존한다. 반려 사유는 고용주에게 보이고 신고자 정보는 보이지 않는다.

CA에서 실제로 근무하는 공고가 대상이다. 고용주의 본사 소재지가 다른 주라는 이유만으로 제한하지 않는다. 원격 전용·타주 근무 공고는 첫 출시 대상으로 홍보하지 않는다.

### 운영자

현재 관리자 화면을 이용해 고용주 요청, 공고, 신고를 하루 두 번 검토한다. 승인된 공고도 즉시 중지할 수 있어야 한다. 악성 계정의 신규 쓰기를 정지하고 공고를 내려야 한다. 조치의 행위자·시간·이유를 audit_logs에 기록한다.

사이트에 없는 기능을 수작업으로 대응할 때에는 명시된 운영 절차를 사용한다. 예: 개인정보 열람·삭제는 지원 이메일로 접수하고 본인 확인 후 처리한다. 24시간 실시간 고객센터를 약속하지 않는다.

## 4. 인증·개인정보 결정

- 출시 필수 로그인은 **Google**이다. Kakao는 이메일 확보, 계정 복귀, 취소/실패 시나리오까지 staging에서 통과할 때 포함한다.
- Naver와 Phone OTP는 첫 출시에서 비활성화하고 미설정 버튼을 공개 로그인 화면에 늘어놓지 않는다. SMS 비용·스팸·이메일 없는 계정 처리를 이번 일정에서 줄인다.
- 기존 phone-only 계정이 있다면 삭제하지 않는다. 공개 전 계정 수를 확인하고 본인 확인을 거쳐 검증된 이메일 연결/접근 방법을 안내한다.
- 표시 이름은 1~80자. 사용자 입력의 이메일을 곧바로 인증된 연락처로 취급하지 않는다. 알림 수신 주소는 Supabase Auth의 확인된 이메일에서 구한다.
- 인증 갱신 쿠키는 현재 request와 response 양쪽에 반영한다. 역할·소유권은 매 요청에서 서버와 DB가 검증한다.
- 운영자 개인의 Google/GitHub/Vercel/Supabase 계정에 MFA를 적용한다. 앱의 관리자 쓰기에도 Supabase AAL2를 요구하고 복구 절차를 준비한다.
- SSN, 여권, 비자 사본, 인종/국적 정보, 이력서 파일은 수집하지 않는다. 지원서·메시지 원문을 로그·분석·알림 이메일에 포함하지 않는다.
- 이용약관·개인정보처리방침·공고 정책·일반 근무자격 안내를 실제 내용으로 게시한다. 운영 주체, 연락처, 실제 처리 업체, 보관/삭제 방식은 대표가 확인한 사실만 게시한다.
- 개인정보 보관 기한과 법적 보존 예외는 출시 전 검토 산출물로 확정한다. 다른 조직의 정책이나 법정 기한을 그대로 복사하지 않는다.

## 5. 공고 데이터·검색 계약

| 항목 | 결정 |
|---|---|
| 지역 | 신규 공고 근무지는 CA. 도시 자유 입력을 trim/공백 정리하고 공개 중인 공고에서 필터 선택지를 생성한다. LA/OC의 9개 도시 제한을 제거한다. |
| 주 검증 | 브라우저의 CA 고정값만 믿지 않고 Server Action과 DB 쓰기에서도 검사한다. 기존 타주 행은 먼저 수량·소유자를 확인하고 공개 중지/보정한다. 임의 삭제하지 않는다. |
| 급여 | 현재 5개 pay_unit을 유지한다. 같은 단위 안에서만 급여 비교. 단위 없이 급여 필터/정렬을 요청하면 hour로 해석하고 UI에도 표시한다. |
| 최소 급여 | 공고의 pay_min이 검색 하한 이상이어야 한다. 현재 pay_max 기반 검색을 바꾼다. |
| 시급 검토 | pay_min > 0과 범위 형식은 DB/서버가 강제한다. 적용 최저임금의 적정성은 지역·업종별 심사 절차에서 판단한다. |
| 공개 조건 | approved AND state = CA AND expires_at > now() AND 소유 계정 active. 목록·상세·지원·사이트맵·구조화 데이터에 동일하게 적용한다. |
| 유효기간 | 승인 시 30일. 운영 정책의 유효기간이며 법정 기간이라는 뜻이 아니다. 연장/재게시에는 재심사를 거친다. |
| 마감 | expired로 전환하고 expires_at을 현재 시각으로 설정. 기존 지원 기록과 대화는 유지한다. |
| 정렬 | posted_at의 전체 timestamp 사용. 날짜 문자열로 잘라 같은 날의 순서를 잃지 않는다. 동률은 id로 고정한다. |
| 페이지 | 공개 목록은 20개+다음 페이지 존재 확인 1개. 관리자·지원 목록도 명시적 페이지, 대화는 최근 50개와 이전 메시지 탐색. |
| 시간 | DB timestamptz는 UTC, 근무시간과 마감 표시는 America/Los_Angeles 및 PT 표기. 일광절약시간을 고정 UTC-8로 처리하지 않는다. |

신규 필드는 필요한 범위로 제한한다. 기존 expires_at, moderation_status, profiles.display_name, audit_logs를 우선 재사용한다. 동의 버전/시각, 계정 정지 상태, 신뢰할 수 있는 알림 큐처럼 현재 필드로 해결되지 않는 정보만 추가한다.

## 6. 상태 전환과 권한

| 행위자 | 허용 |
|---|---|
| 고용주 | 본인 회사 공고 생성→pending; 본인 공고 편집→pending; 본인 공고→paused/expired |
| 관리자(AAL2) | pending→approved/rejected; 공개 공고→paused; 사유 기록; 회사 인증 조정; 계정 정지 |
| 구직자/과거 지원자 | 본인 지원→withdrawn, submitted/reviewing/interview/offered 상태에서 가능 |
| 고용주 | 본인 공고 지원의 submitted/reviewing/interview/offered/rejected 처리; withdrawn 복구 금지 |
| 정지 계정 | 신규 공고·지원·메시지·신고·권한신청 불가. 본인 개인정보 요청 경로는 유지 |

공고와 지원의 상태 변경은 expected_updated_at을 받는 비교 후 갱신 방식으로 충돌을 감지한다. 2명이 같은 항목을 다르게 처리해도 마지막 요청이 조용히 덮어쓰지 않는다. 사용자에게 새로고침 후 재검토하도록 안내한다.

관리자 이유는 audit_logs에 저장한다. 고용주에게는 소유권을 검증한 get_job_review_note RPC로 본인 공고의 최근 검토 사유만 반환한다. 공개 view에 사유·신고자·개인 연락처를 추가하지 않는다.

## 7. 알림과 악용 방지

새 지원, 지원 상태 변경, 메시지, 공고/고용주 심사 결과를 이메일로 안내한다. 관리자에게는 새 고용주 요청·대기 공고·신고를 모아 알린다. 이메일은 짧은 안내와 로그인 후 상세 링크만 포함한다.

**notification_outbox 1개 테이블 + DB transaction에서 event 생성 + 1분 주기 worker + Resend**를 사용한다. 별도 메시지 브로커를 추가하지 않는다. worker는 대상 사용자 ID를 통해 검증된 이메일을 읽고 고정된 사이트 origin으로 링크를 만든다. 계정 정지·탈퇴·알림 수신 설정을 반영한다.

큐 claim은 DB lease와 SKIP LOCKED로 중복 worker를 제어한다. 동일 event ID를 provider idempotency key로 사용한다. 총 시도는 최초 1회와 최대 4회 재시도로 제한하고, 재시도 간격은 1/5/15/60분이다. 계속 실패하면 관리자 검토 대상으로 남긴다. 본래 지원/메시지 저장 성공을 이메일 실패로 취소하지 않는다. 동일 대화의 메시지 이메일은 수신자별 고정된 10분 시간 구간당 1개로 묶는다.

초기 한도는 계정당 공고 5개/일, 지원 30개/일, 메시지 20개/분 및 200개/일, 신고 10개/일, 권한 신청 3개/일이다. 이는 조정 가능한 서비스 운영값이며 출시 후 오탐을 확인한다. DB에서 같은 actor의 동시 요청을 직렬화한 뒤 계산하므로 브라우저 버튼·Server Action을 우회한 직접 Supabase 쓰기에도 적용된다. 전면 CAPTCHA는 도입하지 않고 인증 provider의 보호와 호스팅 WAF를 먼저 사용한다.

## 8. 배포·관측·복구

단일 Next.js 앱을 Vercel에, DB/Auth는 Supabase 미국 지역에 둔다. 앱 function과 DB를 가깝게 배치한다. local / staging / production은 별도 데이터와 인증 설정을 사용한다. PR preview를 운영 DB에 연결하지 않는다.

현재 /api/health는 liveness로 유지한다. 별도의 /api/ready는 설정·공개 DB read를 확인하고 2초 제한에서 실패하면 503을 반환한다. 응답은 ok/unavailable 정도의 상태만 공개한다. proxy에서 health/ready/내부 cron에 사용자 인증 갱신을 수행하지 않는다.

CI는 단위 검사 외에 disposable Supabase에 migration을 처음부터 적용하는 검사, 역할별 실제 DB 테스트, 주요 Playwright 시나리오를 포함한다. 가짜 데이터에 의존하는 빌드는 개발 검증에 한정하고 배포용 build:release는 설정 누락 시 실패한다.

배포는 additive migration→staging 검증→production migration→설정된 production build→smoke→공개 순서다. 앱 되돌리기와 DB 복원은 다르다. 첫 릴리스에서는 구버전과 호환되는 schema 변경만 넣고 migration을 되감는 자동화를 만들지 않는다.

초기 목표는 RPO 24시간, RTO 4시간이다. 실제 백업 복구 실험으로 가능한지 확인한 뒤 운영 기준으로 확정한다. 이 목표가 서비스 이용자에게 제공하는 SLA라는 뜻은 아니다.

## 9. 대표 1명의 운영 설계

주간 작업은 한 번에 검토 가능한 작은 변경으로 Codex에 맡기고, 대표는 우선순위·화면 확인·실제 계정 로그인·법률/사업 정보·배포 결정·고객 대응을 맡는다. Codex가 법률 판단이나 고객 커뮤니케이션을 독자적으로 완료했다고 가정하지 않는다.

매일 오전/오후 20~30분씩 승인·신고·실패 알림을 확인한다. 일반 검토/문의는 1영업일 이내 첫 응답을 목표로 공개한다. 즉각 조치가 필요한 신고는 발견 즉시 공고를 중지한다. 대표 부재 중 위험 공고를 방치하지 않도록 신규 공고의 자동 공개는 하지 않는다.

심사 대기가 20건 또는 2영업일을 넘으면 광고/대량 유입 캠페인을 멈추고 검토를 우선한다. 가입과 공고 탐색을 초대제로 되돌리는 대신 처리 예상 시간을 안내한다.

## 10. 출시 완료 조건

1. 샘플 공고가 운영 build/start 어느 경로에도 노출되지 않는다.
2. 확인되지 않은 High/Critical 운영 의존성 경고가 남아 있지 않는다.
3. 실제 Google 로그인부터 CA 공고 승인→지원→답장→철회/마감까지 성공한다.
4. 다른 고용주의 지원자·메시지 접근, 자기 승인, 역할 위조, 정지 계정 쓰기를 실제 DB가 차단한다.
5. 정책 4개와 연락처가 실제 내용으로 게시되고 개인정보 요청 처리를 리허설한다.
6. 알림 실패·재시도·중복·정지/탈퇴 수신자 사례를 검증한다.
7. 대표가 신고 접수부터 게시 중지, 이력 확인까지 직접 수행할 수 있다.
8. CA 다른 도시 3곳 이상, 모바일 390px·데스크톱 1440px, 키보드·iOS Safari를 확인한다.
9. readiness 경보와 백업 복원·앱 rollback을 리허설한다.
10. 정책/보안 차단 사유가 없고 대표가 출시 체크리스트를 확인한다.
